# 给其他 AI 的评审提示词

下面内容可以直接复制给另一个 AI，并把整个 `docs/ai-review` 目录和 OrionAdmin 源码一起提供给它。

---

请对这个 Avorion 中文服务器管理软件做一次严格的产品、UX 和源码架构评审。先阅读 `docs/ai-review/README.md`，再依次阅读：

1. `01_PRODUCT_SCOPE_AND_CURRENT_STATE.md`
2. `02_SCREENSHOT_INDEX.md`
3. `03_UX_AND_LAYOUT_AUDIT.md`
4. `04_MODULAR_MONOLITH_AND_EXTENSION_GUIDE.md`
5. `05_ROADMAP_AND_BACKLOG.md`
6. 根目录 `06_CAPABILITY_MATRIX.md`、`07_MODULAR_ARCHITECTURE.md`、`08_INVENTORY_ITEM_CATALOG_AND_ICONS.md`

请同时检查 `docs/ai-review/screenshots/current/` 中 11 个页面的两档截图，以及 `screenshots/feature-states/` 的 Inventory 深层状态和 JSON 报告。

重要事实和边界：

- 当前截图时 Avorion 服务端已停止。玩家、联盟、星区和奖励目标出现 503 是正常运行状态，不等于功能没实现。
- 不允许用 Mock、推测或假数据掩盖缺失能力。
- 当前产品必须保持模块化单体：一个 .NET API/Agent 进程、一个 React 前端、一个专用 OrionAdminBridge MOD、一个 SQLite 数据库、一个部署包；不要建议拆微服务。
- `Program.cs` 必须保持 composition root；HTTP 路由体按业务域放在 Endpoint 模块；写操作通过 Operation/队列/Worker；Agent 承担 RCON/进程/文件的真实实现；管理 MOD 命令文件只做薄路由。
- 玩家在线、位置、资产和 Inventory 归玩家管理；联盟详情归联盟管理；舰船归舰船管理；奖励、活动和星区建设归游戏管理。另一个页面只能显示完成其任务所需的最小上下文。
- 不提供任意 Lua、任意 RCON、任意控制台；不自动管理第三方 Workshop MOD；不把剧情/BOSS 物品加入普通发放白名单。
- 当前后端和 MOD 边界总体健康，但 `frontend-prototype/src/pages/ServerUpdatePage.tsx` 有 2403 行，是已确认的前端技术债。
- 共享物品目录已有 58 个定义、19 种普通炮塔、39 个系统插件和真实静态图标；只有 11 个系统插件已验证可发放。图标存在不等于物品可发放。

请输出以下内容：

## A. 页面和信息架构

- 逐页指出最影响使用的 1–3 个问题，引用具体截图文件名。
- 检查信息是否重复、是否放错主页面、是否缺少任务所需上下文。
- 对停服空态、运行态、失败态和危险操作提出一致规则。
- 判断哪些未实现导航应隐藏、禁用或显示“规划中”。
- 不要只说“更现代、更简洁”，要说明具体删什么、合并什么、移到哪里、为什么。

## B. Inventory 工作台

- 评审当前嵌套弹窗布局。
- 给出单层三栏工作台的详细信息结构：分类/筛选、物品列表、参数/预览/确认。
- 说明炮塔的类型、材质、科技、稀有度、Seed、DPS 等参数怎样分组，哪些是输入、哪些是服务器生成结果。
- 保留 11 个已验证、33 个仅目录、14 个剧情禁止的显式策略。
- 不假设可以导出程序化炮塔三维缩略图。

## C. 模块化单体

- 检查现有目录和依赖方向，指出跨层、过大文件、重复模型和潜在耦合。
- 给出拆分 `ServerUpdatePage.tsx` 的文件级方案，但保持一个 `/server/update` 路由和原有页面职责。
- 为未来 `ships`、`game-events`、`sector-construction`、`inventory/turrets` 提供 feature 边界。
- 每条建议说明“现在改”还是“达到什么条件再改”；不要为了形式增加过多抽象。
- 不要建议微服务、事件总线集群、独立数据库或云基础设施，除非未来多节点需求已真正出现。

## D. 路线图与风险

- 审查 M0 更新页拆分 → M1 炮塔 → M2 舰船/货舱/船员 → M3 海盗活动 → M4 星区建设的顺序。
- 指出哪些里程碑可以调整，以及调整的证据。
- 为每个里程碑列出最小可交付范围、禁止范围、真实服验证和退出/回滚条件。
- 把建议严格分为：已支持、已确认可开发、待验证、不支持/不做。

## E. 最终建议格式

请按严重度输出：

1. `P0`：会造成数据破坏、安全问题或关键流程不可用。
2. `P1`：继续开发前应该解决的架构/交互问题。
3. `P2`：明显改善效率、一致性或可维护性的优化。
4. `P3`：可选美化或长期建议。

每条问题必须包含：证据文件、影响、建议改法、涉及模块、验证方法。最后给出一个按依赖排序的 5–10 项执行清单。不要直接修改源码，先给评审结论。

## 希望其他 AI 特别回答的问题

1. 在不增加重复页面的前提下，玩家、联盟、舰船、活动、星区建设之间的导航怎样设计最顺？
2. 哪些当前 KPI 卡和空态属于重复信息，可以合并？
3. Inventory 三栏工作台在 1440×900 下应怎样分配宽度和滚动区域？
4. 更新页拆分后，共享流程状态应放 hook、状态机还是页面 reducer？为什么？
5. 后端当前 17 个 Endpoint 模块是否需要进一步按 feature 命名空间整理，还是保持现状更合适？
6. 炮塔生成、舰船船员补充、海盗活动、星区模板应各自有哪些幂等和结果复核字段？
7. 哪些“看起来能做”的功能其实应该继续留在待验证区？
