# 布局与 UX 审查

审查范围：本次 11 个现有路由的 1440×900、1920×1080 截图，以及已验证的 Inventory/物品目录深层状态。审查基于静态桌面截图与机器报告；没有把它夸大成完整移动端、键盘、屏幕阅读器或所有写流程验收。

## 1. 整体判断

当前 A 风格方向是成立的，不建议推倒重做：深蓝侧栏、浅灰工作区、白色卡片、蓝色主操作、绿色成功、橙色警告、红色危险，已经形成稳定的管理后台语言。服务器八个子页也有统一页头、标签导航和服务器状态入口。

真正需要解决的不是换一套视觉风格，而是：

1. 停服/空数据时部分页面出现过大的空白工作区。
2. 相同事实在同一页面重复出现，尤其自动任务空态。
3. 未实现的导航和已经实现的页面外观一致，用户只有点后才知道不可用。
4. 更新页流程太多，代码与认知负担都集中在一个页面。
5. Inventory 的“详情弹窗里面再开物品目录弹窗”层级不合理。

## 2. 当前设计的优点

- 状态真实：玩家、联盟、星区在停服时明确显示不可用，没有填充虚构数据。
- 风险色使用克制：备份恢复、强制终止等高风险动作才使用红色。
- 页面职责大体清楚：奖励中心只保留目标身份和礼包，不复制玩家在线、位置、资产。
- 服务器八个标签页的导航位置和结构一致，减少学习成本。
- 1920×1080 和 1440×900 两档均没有横向溢出。
- 日志页的信息密度符合运维场景，操作记录和实时日志来源区分明确。
- 备份页把“备份记录”和“恢复流程”并列，管理员可以在执行前理解风险。
- 页面文案经常说明数据来源和边界，这对服务器管理工具很重要。

## 3. 优先问题

### P1：未实现导航缺少可见状态

证据：侧栏的“总览、舰船管理、MOD 管理、文件与配置、设置”与可用入口视觉相同；游戏管理的“活动中心、星区建设、活动记录”也表现成正常标签。

风险：用户会认为点击没反应是程序故障，而不是功能尚未开发。

建议：

- 没有路由的侧栏项在正式版中暂时隐藏，或增加清晰的“规划中”标记和禁用样式。
- 计划页只有在至少具备可交付的只读内容时才进入主导航。
- 游戏管理未完成标签可保留为路线图提示，但必须是不可交互状态，旁边显示“规划中”，不能弹一个泛化 toast 就结束。

### P1：Inventory 嵌套弹窗造成层级和空间问题

证据：物品目录当前从玩家/联盟详情内打开，形成详情弹窗中的第二层目录弹窗；目录本身约 978px 宽且内容密集。已有专项审查见 `frontend-prototype/qa/inventory-catalog/layout-audit-2026-09-10.md`。

风险：关闭层级不清楚、焦点返回复杂、1440 宽度下压迫感强；日后加入材质、科技、稀有度、Seed、DPS 预览后会继续恶化。

建议采用单层三栏工作台：

| 左栏 | 中栏 | 右栏 |
|---|---|---|
| 分类、搜索、发放策略筛选 | 图标网格/列表和关键摘要 | 选中物品详情、参数、预览、确认入口 |

- 玩家/联盟详情内的“Inventory”入口打开一个单层大抽屉或全宽工作区，而不是再套一层 modal。
- “浏览目录”和“准备发放”是同一工作流：目录项只在右栏进入参数与确认，不另开第三层。
- 目录图片用于快速辨认；技术等级、材料、稀有度、炮塔战斗参数仍以文字和数值为准。
- 11 个已验证可发放、33 个仅目录、14 个剧情禁止必须在筛选和详情中都有一致标识。

### P1：更新页承担过多状态和流程

证据：`ServerUpdatePage.tsx` 当前 2403 行；同一页面承担未配置、检测、全新安装、已有路径、基础配置、验证、更新管理等多阶段内容。

风险：任何小改动都可能影响其他阶段；视觉一致性和回归测试成本会持续升高。

建议：保留同一个 `/server/update` 路由和页面职责，不新增一堆重复页面，但把内部流程拆成独立步骤组件和 hooks。页面壳只负责当前阶段、步骤切换和共享状态。架构拆分方案见 `04_MODULAR_MONOLITH_AND_EXTENSION_GUIDE.md`。

### P1：停服空态没有提供下一步

证据：玩家、联盟、内存与星区页面都准确显示“服务端未运行”，但主要内容区仍保留完整大表格/双栏高度。

风险：真实性很好，但用户知道“不可用”后仍不知道最快如何恢复。

建议：

- 顶部错误条保留，空态增加两个明确入口：`启动服务器`、`运行诊断`。
- 停服时将大表格压缩为约一个任务卡的高度；服务器恢复后再恢复完整工作区。
- 不在空态复制控制页所有状态，只显示导致当前任务不可完成的最小原因。

### P2：性能页混合“当前不可用”和历史运行数据

证据：顶部 CPU/内存显示 `—`，但 24 小时曲线和均值仍有历史数据。

风险：管理员可能误以为曲线正在实时更新，或把历史峰值当成当前异常。

建议：

- 图表增加明确分段：`最近一次运行区间`、`服务器停止于 xx:xx`。
- 当前值与历史统计分别放在标题和图例中，避免把 `CPU 当前 —` 与历史 100% 峰值放得同样醒目。
- 对采样中断显示断线/阴影区，而不是用连续趋势暗示当前仍运行。

### P2：自动任务空态重复

证据：顶部统计写 0，左侧列表写“还没有自动任务”，右侧又写“暂无已启用任务”。

建议：保留顶部统计；主区域只保留一个包含“新建任务”的空态。右侧“下一次执行”在存在至少一个启用任务后再出现。

### P2：诊断未运行状态过于展开

证据：11 项检查均显示相同的“运行诊断后显示真实结果/待检查”，占据三列大卡片。

建议：未运行时显示一张紧凑检查说明和主按钮；运行后再展开三组结果。这样首屏更有行动导向，也避免重复文字。

### P2：更新入口文案层级不够直观

证据：用户已经位于“服务器更新”页，底部仍有“进入更新管理”。

建议：按钮改成具体动作，如“检查官方版本”或“开始更新检查”；把环境验证看成前置状态，不再让用户判断“当前是不是已经进入更新管理”。

## 4. 页面职责与避免重复

| 页面 | 唯一主责 | 可以引用的最小上下文 | 不应出现 |
|---|---|---|---|
| 服务器管理 | 安装、配置、启停、性能、内存、更新、任务、备份、日志、诊断 | 无 | 完整玩家/联盟/奖励工作台 |
| 玩家管理 | 玩家在线、位置、资产、Inventory、单人动作、关联舰船入口 | 必要服务器可用状态 | 在奖励页再复制一套玩家在线列表 |
| 联盟管理 | 联盟成员、职级、资产、Inventory、关联舰船入口 | 必要服务器可用状态 | 在星区建设页复制完整联盟详情 |
| 舰船管理 | 舰船、货舱、船员、系统、蓝图和创建 | 玩家/联盟名称与归属 | 把完整舰船编辑器塞回玩家详情 |
| 游戏管理 | 批量奖励、活动、星区建设和活动记录 | 最小目标身份、服务器是否可执行 | 玩家在线状态、个人资产、完整舰船详情 |
| MOD 管理 | 读取第三方 MOD、配置、Workshop ID 线索和相关错误 | 服务器路径和错误摘要 | OrionAdminBridge 的游戏玩法操作 |

只有当另一个页面的核心动作确实依赖某项信息时才引用，而且只显示完成决策所需的最小字段。

## 5. 推荐的信息架构

主导航建议按“已可用”和“规划中”分层，不因为规划里有功能就提前铺满侧栏。

- 总览：等跨模块摘要规则确定后再开放。
- 服务器管理：控制、性能、内存与星区、更新、自动任务、备份、日志、诊断。
- 玩家管理：在线列表 → 玩家详情 → 资产 / Inventory / 单人动作 / 舰船入口。
- 联盟管理：联盟列表 → 成员 / 资产 / Inventory / 舰船入口。
- 舰船管理：舰船列表 → 舰船详情 → 货舱 / 船员 / 系统 / 蓝图。
- 游戏管理：奖励中心、活动中心、星区建设、活动记录。
- MOD 管理、文件与配置、设置：达到最小可用后再显示为正常入口。

## 6. 设计语言继续保留的规则

- 不换掉现有深蓝侧栏和浅色卡片体系。
- 同一风险级别使用同一颜色：蓝色普通动作、绿色已验证/成功、橙色降级/需要注意、红色不可逆或紧急。
- 每页只保留一个最突出的主操作；次要动作使用描边或文本按钮。
- 列表型工作应优先给可扫描表格/列表，不用大量 KPI 卡装满页面。
- 空态说明必须包含“为什么”和“下一步”，但不重复完整的上游页面。
- 长流程使用步骤、阶段组件和明确返回路径，不把所有阶段一次渲染在一个巨型组件。
- 物品、舰船、星区模板等高密度功能优先采用列表/网格 + 详情检查器，而不是连续弹窗。

## 7. 后续视觉验证清单

每次新增页面或大改布局，至少检查：

1. 1440×900 和 1920×1080 的首屏与全页。
2. 服务器运行、停服、接口失败、空列表、有真实数据五类关键状态。
3. 无横向溢出、无内容被固定侧栏/弹窗裁切。
4. 主按钮、危险按钮、禁用态和加载态有明确差异。
5. 弹窗关闭、焦点返回、Esc、Tab 顺序和确认文本可用。
6. 浏览器 console、page error 和失败请求被记录；预期 503 与真正前端错误分开。
7. 不把截图通过当成完整可访问性合规；仍需键盘、对比度、可访问名称和屏幕阅读器检查。
