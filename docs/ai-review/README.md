## 事实分级

评审和后续开发统一使用四种状态：

| 状态 | 含义 |
|---|---|
| 已支持 | 源码已实现，并至少通过自动测试；关键游戏写操作还有真实服务器复核 |
| 已确认可开发 | 官方 API 或同版本原版脚本有明确依据，但 OrionAdmin 尚未实现 |
| 待验证 | 底层能力不完整，安全边界、持久化或真实行为还不能承诺 |
| 不支持/不做 | 官方限制、授权排除或风险不可接受，不设计成可点击入口 |

任何 UI、测试夹具、物品图标或原版脚本的存在，都不能单独把能力升级成“已支持”。完整总账以根目录 `06_CAPABILITY_MATRIX.md` 为准。

## 交给其他 AI 时的边界

请让评审者优先回答：

1. 页面层级和信息密度怎样优化，而不复制玩家在线状态、资产或联盟列表？
2. Inventory 物品选择器怎样从嵌套弹窗改成单层、可搜索、可比较的三栏工作台？
3. 如何先拆分 2403 行更新页，再接入炮塔、舰船、活动和星区建设？
4. 新功能应该复用哪个领域模块，哪些功能必须新建 feature，而不是把接口继续堆进现有文件？
5. 哪些建议会破坏真实数据原则、写操作安全或模块化单体边界？

不要让评审者根据停服空态得出“玩家/联盟/Inventory 没做”的结论，也不要让其凭截图猜测不存在的 Avorion 接口。
