# AI 开发与跨电脑同步流程

## 资料归属

- README：所有 AI 和开发者的阅读入口。
- PLAN：步骤编号、依赖和当前状态的主表。
- HANDOFF：当前工作现场、验证结果、阻塞和下一步。
- DECISIONS：用户明确决定与方案取舍；记录来源，不把建议写成授权。
- 01_USER_REQUIREMENTS / 06_CAPABILITY_MATRIX / 07_MODULAR_ARCHITECTURE：详细需求、能力边界、架构。
- docs/evidence 与设计 QA：经过检查的必要证据，注明日期、代码版本和环境性质。
- Git 历史：每一次实际代码变更。托管平台 Issue/看板用于展示与讨论，结论仍需回写仓库文档，保证克隆后可独立接续。

## 每次开始

1. 新电脑先克隆；已有目录先看 git status、当前分支和远端。
2. 有未提交修改先妥善保留，不直接覆盖。工作区适合更新时，用 git pull --ff-only；分叉时检查并解决，不用强推或硬重置规避。
3. 阅读 HANDOFF 与 PLAN，只领取一个范围清楚的步骤；记录进行中。
4. 检查相关源码和规则；发现旧状态与代码不符时记录证据再更新。

## 每个可交接的小步骤结束

1. 完成修改，并执行与变更相符的验证。仅文档修改检查链接和内容；业务修改运行相关测试。
2. 更新 PLAN 和 HANDOFF；能力变化同步能力矩阵，用户决策同步 DECISIONS。
3. 检查 git diff 和拟提交文件；不上传密码、运行数据库、Galaxy、日志全集或本机进程档案。
4. 把代码和对应进度放在同一个提交中，提交信息包含任务编号，例如 M1-02: add turret preview。
5. 推送到已确定的远端分支，核对远端提交 SHA；在交付消息中分别报告验证结果与同步结果。
6. 网络失败时说明“已本地提交，未远端同步”，保留提交等待补推；没有推送成功就不能称已经备份到网站。

写下规则不会自动产生提交或上传。每次仍须实际执行 commit、push 和远端核对。聊天中途中断可能留下未提交修改，因此以小步骤建立检查点；未完成代码可放工作分支并如实注明状态。

## 换电脑

结束旧电脑工作时提交并推送检查点；新电脑克隆或拉取相同分支。两台电脑不同时修改同一工作分支。
有并行开发需求再使用独立分支和合并请求。不要用网盘同时同步 .git 工作目录。
Git 仓库保存开发资料，游戏存档和本机秘密另行备份。

## 平台上展示进度

如果选 GitHub，可把任务编号映射成 Issues，用 Projects 展示：待开始 / 进行中 / 待验证 / 已完成 / 阻塞。
先完成仓库内主表，后续再建立映射。不要维护两份相互矛盾的任务清单；平台讨论中的决定在本次提交内回写文档。
自动 CI 可验证构建和部分测试，不能替代真实游戏写入、重启保存或人工设计验收。

## 本仓库已配置的同步方式

远端为 https://github.com/wager-code/Avorion-Orion-Manager，公开仓库，main 分支。
本次首传使用已连接的 GitHub 工具；命令行 Git 尚未完成写入登录。后续不能把已绑定 origin 误当成已具备 git push 凭据。
使用 GitHub 工具上传时，保持路径和二进制内容完整，按可审查批次提交，核对最终 Git 树；更新分支后再读回远端结果。不要强推覆盖未知变更。
本机有本地导入备份分支 local-import-baseline；正常开发使用 main，不把备份分支误当成最新进度。
