# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

The confirmed primary-navigation label for the server module is `服务器管理`, not `服务器`. Keep this wording consistent in the sidebar, page heading, and breadcrumbs.

For `服务器管理 → 备份`, backup records come from scanning the server's automatically generated save-backup files. The record list may show only data the program can reliably read from those files: backup time, file size, availability status, and restore operation. Do not invent backup-type/source metadata or type-based filters/counts.

For `服务器管理 → 日志`, the confirmed visual direction is a single white workbench card containing a dark ink-blue realtime log reader. Keep the scope limited to real filesystem logs, the real SSE stream, search, Error / Warning / Player / MOD / RCON / Save filters, auto-scroll, and copying visible logs. Never generate Mock log lines; unavailable paths, empty files, disconnection, and reconnection must be shown truthfully. Do not add export, clear, pause, source switching, retention settings, charts, or log metrics unless the user later confirms them.

For `服务器管理 → 诊断`, the confirmed visual direction is a wide server-health summary followed by three grouped result cards: `服务与连接`, `运行环境`, and `数据与运行状态`. Keep the scope limited to the 11 confirmed checks, one compact six-hour memory trend, readable Chinese results, and rerunning the real Server Agent diagnosis. Never use Mock diagnostic values; unavailable probes and insufficient history must remain visibly unavailable. Do not add repair actions, terminal access, export, history, alerts, network scans, configuration editing, or extra diagnostic items unless the user later confirms them.

For `服务器管理 → 更新`, SteamCMD installation, Avorion server installation, existing-path import, path detection, and later path management stay inside the existing Update route rather than becoming a permanent sidebar page. The implemented flow is `未配置 → 真实自动检测/手动选择 → 真实路径验证并保存 → 更新环境就绪但管理配置未完成`. Path confirmation must explicitly state that it does not move files or start an update. Real read-only directory browsing, bounded installation detection, path validation, local configuration persistence, and the narrowly scoped `server.configure` operation are now connected. Keep update execution and firewall writes locked until their safety contracts are verified.

On 2026-09-07 the user explicitly approved a dedicated server-side management MOD and its M1 isolated capability validation. OrionAdminBridge may supply individually verified game data. See `../17_MANAGEMENT_MOD_STAGE_M1.md`. This supersedes the older blanket ban only for our dedicated component; third-party `MOD 管理` remains read-only. The component's planned install/version area belongs inside Server Management → Update, and requires the established per-page visual approval before UI implementation. Unverified game data/actions remain unavailable rather than Mock. The legacy setup field `installManagementMod` stays false until a separate component-install operation is implemented; do not silently install via the old wizard.

All frontend API mutations must use `src/lib/api.ts`. It establishes the short-lived local administrator session and attaches the CSRF token; do not call `fetch` directly for POST, PUT, PATCH, or DELETE. Long-operation requests must additionally send a stable 8–128 character `Idempotency-Key`. The R2 safety foundation does not unlock any server command by itself.

`steamcmd.install`, `avorion.install`, `server.configure`, `server.initialize`, `server.start`, `server.save`, `server.shutdown`, `server.restart`, `avorion.update.check`, `avorion.files.verify`, and `avorion.update.rollback-point.create` are the currently verified commands. The update check is fixed to anonymous App 565060 / public and may only query app info after Valve signature validation. File verification is read-only PE-header/size/SHA-256 inspection and must never run `app_update validate`, repair, or overwrite files. The update rollback point is a separate safety artifact beside the server directory: it may be created only while stopped, copies both the full server installation and managed Galaxy, rejects reparse points, verifies every copied file with SHA-256, and atomically publishes a manifest. It is not an Avorion `.bak` record, must not appear on the Backup page, and does not authorize or perform restore. Update operations must persist and restore their Operation IDs across navigation and surface true progress and safe failure evidence. Full `avorion.update`, rollback execution, and `server.force-stop` remain locked. The install/configure/initialize/control safety contracts remain unchanged.

The confirmed path-selection UX must not require users to pre-create folders or copy paths from Windows Explorer. Browser UI must browse the Server Agent host through a real read-only API (never browser-local folder access and never Mock directory data). For a fresh install, users choose an existing parent directory and can edit the child-folder name; the verified install operation creates that child directory. Keep manual path entry as an advanced fallback. Never create a directory outside the verified SteamCMD or Avorion installation operation.

The three-step server setup wizard is `Galaxy 与基本信息 → 网络与 RCON → 检查与启动`. It persists only non-sensitive draft fields and performs real preflight against the saved update environment, Galaxy path, input constraints, and host TCP/UDP listener tables. The RCON password must never appear in the draft, launch profile, operation evidence, logs, or responses; it may exist only in request/worker memory and, for an existing Galaxy, in the actual Avorion-required `server.ini`. A new Galaxy has no `server.ini` before first start, so the successful operation must report `launch-profile-ready` and defer RCON instead of fabricating the file. Game listen address and independent Query-port writes are not verified for the target version, while firewall and process start remain separately locked; show them as deferred rather than completed. The compatibility-only `installManagementMod` API field must always be sent and stored as `false`.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.
